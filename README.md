# Call Integration Service

Сервис получает события о результатах звонков из RabbitMQ, проверяет их и
сохраняет кампании и звонки в MongoDB. Consumer работает внутри FastAPI;
HTTP API возвращает звонки выбранной кампании. Пример producer публикует четыре
события для двух кампаний.

## Быстрый запуск на Windows

Нужны Python 3.12, Docker Desktop с работающим Linux engine и Docker Compose.
Из корня проекта в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python -m pip install -e ".[dev]"
Copy-Item .env.example .env
docker compose up --build -d
docker compose ps
.\.venv\Scripts\python producer.py
Invoke-RestMethod http://127.0.0.1:8000/campaigns/camp_001/calls
```

Дождитесь состояния `healthy` у трёх сервисов в `docker compose ps` перед
запуском producer. Обработка асинхронная: если запрос вернул ещё не все звонки,
повторите его. Для `camp_001` и `camp_002` ожидается по два звонка. Повторный
запуск producer не создаёт дубликаты. Для остановки используйте
`docker compose down`: именованные volumes при этом сохраняются.

На Linux/macOS с Python 3.12 и Docker Compose:

```sh
python3.12 -m venv .venv
./.venv/bin/python -m pip install -e '.[dev]'
cp .env.example .env
docker compose up --build -d
./.venv/bin/python producer.py
curl http://127.0.0.1:8000/campaigns/camp_001/calls
```

`.env.example` содержит только локальные демонстрационные значения. На хосте
используются `127.0.0.1` и порты API `8000`, AMQP `5672`, Management `15672`,
MongoDB `27018`. Все они опубликованы только на loopback. Внутри Compose
приложение подключается к `mongo:27017` и `rabbitmq:5672`. При изменении
портов согласуйте параметры `.env`, включая `RABBITMQ_PORT` с `AMQP_PORT` и
`RABBITMQ_MANAGEMENT_URL` с `RABBITMQ_MANAGEMENT_PORT`. Учётные данные RabbitMQ
инициализируются при первом создании volume; изменение `.env` само по себе не
меняет пользователя в существующих данных брокера.

## API

- `GET /campaigns/{campaign_id}/calls` — JSON-массив звонков кампании без
  MongoDB `_id`, сортировка по `created_at`, затем `call_id`. Для существующей
  кампании без звонков возвращается `200` и `[]`.
- Если кампания отсутствует, тот же маршрут возвращает **HTTP 200**,
  `text/plain; charset=utf-8` и точный текст `Кампания не найдена`.
- `GET /health` — проверка живости процесса без обращения к зависимостям.
- `GET /ready` — MongoDB ping с таймаутом, состояние RabbitMQ connection,
  channel и consumer: 200 при готовности, иначе 503.
- Swagger UI: `http://127.0.0.1:8000/docs`; OpenAPI: `/openapi.json`.
  В документации описаны JSON и текстовый варианты ответа HTTP 200.

## Контракт события

Тело сообщения — UTF-8 JSON, например:

```json
{
  "schema_version": 1,
  "campaign": {
    "campaign_id": "camp_001",
    "name": "Напоминание о платеже",
    "created_at": "2026-10-20T10:00:00Z"
  },
  "call": {
    "call_id": "call_0001",
    "campaign_id": "camp_001",
    "phone": "79001234567",
    "status": "success",
    "created_at": "2026-10-20T10:06:00Z"
  }
}
```

`schema_version` сейчас равна `1`; `campaign` описывает кампанию, `call` —
результат звонка. `message_id` передаётся в AMQP properties, а не в JSON.
Идентификаторы кампании в двух объектах должны совпадать, обязательные строки
не могут быть пустыми, телефон передаётся строкой. `status` не ограничен enum.
Время должно содержать часовой пояс и нормализуется к UTC; MongoDB хранит его
с точностью до миллисекунд. Неизвестные поля запрещены. Всё событие проверяется
до первой записи.

## Архитектурные решения

1. **FastAPI lifespan и один worker.** Lifespan создаёт подключения, индексы и
   consumer и закрывает их при остановке. Один worker создаёт один consumer
   внутри приложения, как требуется в задании.
2. **PyMongo Async.** Асинхронный драйвер позволяет выполнять запросы MongoDB
   без блокирования event loop FastAPI и consumer.
3. **Quorum queue.** `calls.queue` — durable quorum queue RabbitMQ 4.3; она
   поддерживает выбранные native delayed retry и at-least-once dead-lettering.
4. **Native delayed retry.** При локальном временном сбое MongoDB
   `reject(requeue=True)` передаёт задержку и счётчик доставок брокеру. Это
   ограничивает число повторов и не удерживает consumer в бесконечном цикле.
   При глобальной недоступности MongoDB текущая доставка удерживается без ACK,
   чтобы не расходовать лимит для очереди сообщений.
5. **DLQ.** Невалидный JSON или схема, конфликт бизнес-данных и исчерпание
   `delivery-limit` направляются через `calls.dlx` в `calls.dlq`; последующие
   корректные сообщения продолжают обрабатываться.
6. **Manual ACK после MongoDB.** Подтверждение отправляется после проверки и
   сохранения кампании и звонка. При потере соединения до ACK брокер может
   доставить сообщение повторно.
7. **Unique indexes и upsert.** Уникальные `campaign_id` и `call_id`,
   `$setOnInsert` и сравнение сохранённых полей позволяют безопасно обработать
   повтор и обнаружить конфликт данных с тем же бизнес-ID.
8. **Без multi-document транзакции.** Кампания без звонка допустима как
   промежуточное состояние; повтор доставки достраивает звонок. Транзакция
   MongoDB не сделала бы запись и RabbitMQ ACK атомарными.
9. **Неизменяемый результат звонка.** Это явное допущение: исходное задание не
   описывает обновление результатов. Другое содержимое с тем же `call_id`
   считается конфликтом, а не перезаписывает данные.
10. **structlog.** События приложения и Uvicorn имеют уровень и UTC timestamp;
    Docker выводит JSON, локальный запуск — читаемый текст. Логи обработки не
    содержат телефон и payload, access log исключает query string.
11. **Раздельные `/health` и `/ready`.** Liveness остаётся доступным при отказе
    внешней системы; readiness исключает приложение из готовых, пока MongoDB,
    RabbitMQ или consumer недоступны.

## Гарантии и ограничения

Доставка имеет семантику **at-least-once**: подтверждение может потеряться и
сообщение может прийти повторно. Идемпотентность обеспечивается по бизнес-ID
при совпадении полей; конфликтующие данные отклоняются. Кампания может
существовать до записи её звонка, если обработка прервалась между записями.
Конфликт звонка тоже может оставить новую кампанию без звонков: запись кампании
идёт первой, а multi-document транзакция не используется.

DLQ не возвращается в основную очередь автоматически. Оператору нужно
исследовать причину, исправить данные или инфраструктуру и выполнить контролируемый
redrive. `reject` запрашивает dead-lettering; его фактическое завершение зависит
от доступности DLX и DLQ. Политика очереди и её фактическое применение проверяются
скриптом ниже.

Один контейнер MongoDB и один RabbitMQ не обеспечивают высокую доступность.
Текущий Compose предназначен для локальной проверки: для production потребуются
подходящая кластеризация и резервное копирование, управление секретами, защита
доступа и внешнее наблюдение за сервисом и DLQ. При длительной потере RabbitMQ
supervisor завершает приложение для перезапуска контейнера.

## Тестирование

В командах ниже `python` означает интерпретатор из созданного окружения:
`.\.venv\Scripts\python` на Windows или `./.venv/bin/python` на Linux/macOS.

Для unit-тестов внешние сервисы не нужны. Integration-тесты требуют MongoDB и
RabbitMQ и используют отдельные базы и очереди с уникальными именами. Для
проверок отказов запускайте их в отдельном Compose project командой
`python tests/e2e/run_e2e.py --integration`: она также трижды повторяет тест
восстановления соединения. Прямой запуск pytest рассчитан на выделенные тестовые
сервисы; `TEST_MONGO_URL` по умолчанию — `mongodb://127.0.0.1:27018`. Для других
портов задайте его вместе с параметрами RabbitMQ и Management API. Тесты удаляют
созданные ими базы и очереди; рабочие коллекции и volumes не очищают.

```powershell
python -m ruff check .
python -m pyright
python -m pytest tests/unit -q
python -m pytest tests/integration -q
python tests/e2e/run_e2e.py --integration
python scripts/verify_rabbitmq.py
python tests/e2e/run_e2e.py
```

E2E создаёт Compose project с уникальным именем, свободными localhost-портами и
собственными volumes и тегом образа. Он собирает сервис, проверяет API, повторную публикацию,
топологию, DLQ, retry, остановку и восстановление RabbitMQ и MongoDB, а также
перезапуск приложения supervisor. Перед удалением тестовых volumes скрипт проверяет
их принадлежность созданному project. Запуск требует работающего Docker Desktop
и может занять несколько минут; обычный Compose project он не останавливает.
